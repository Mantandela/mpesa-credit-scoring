# Nuru

AI-based credit scoring for informal-sector vendors using M-Pesa transaction data (case: M-Pesa).
Final-year project, BSc Applied Computer Technology, USIU-Africa.

> **Everything here is simulated.** The statements, vendors, loans and repayment outcomes are synthetic, generated by
> this project. No real money moves and no real customer data is used. The numbers describe how well the method
> recovers a simulated outcome, not how it would perform on real borrowers.

## What it does

A vendor uploads an M-Pesa statement (Excel or CSV) and gets a 300-850 score with plain-language reasons, ratings for
seven areas of business health and an estimated loan limit. To apply to a lender, the vendor uses a saved score check
from the last 30 days (no second upload): the application is bound to that check and is sent only if the check's
estimated limit allows the amount. The lender sees a
summary snapshot only (score, risk level, reasons, the request), never the statement, and approves or declines; the
decision is final. Statements are read once in memory and never stored. Three roles, vendor, lender and admin, are
enforced on the server for every page and every action. Lenders later record what happened to approved loans, which
builds a labelled dataset for a future, manually reviewed retraining.

## Quick start

Python 3.11 in a conda environment named `creditscore`:

```
conda create -n creditscore python=3.11
conda activate creditscore
pip install -r requirements.txt
```

The model files (`models/`) and the generated data (`data/`) are not in the repository. Build them once, from the
repo root, in this order (the full dataset has about 10 million statement rows, so the first steps take a while):

```
python src/generator.py         # synthetic statements, vendors and loan applications (seed 42)
python src/clean.py             # transaction types and validation flags
python src/features.py          # 52 leakage-free features per application
python src/scorecard.py         # simulated outcomes from the cash-flow scorecard
python src/train_models.py      # trains and saves the models, writes docs/model_report.md
python src/build_reference.py   # models/reference.json, needed to score a new statement
```

Then create the first accounts and start the app:

```
python scripts/create_demo_users.py
streamlit run app/main.py
```

`create_demo_users.py` creates a demo vendor, two demo lenders and the first admin. Passwords come from the
environment variables it lists (`DEMO_ADMIN_PASSWORD` and so on) or are generated and printed once; none is stored in
plain text or in the repository. The admin then adds further lenders or admins in the app. Details:
[docs/database.md](docs/database.md#demo-users).

**Database.** With no `DATABASE_URL` set, the app uses SQLite at `data/private/app.db`. Set `DATABASE_URL` (in the
environment or in `.streamlit/secrets.toml`, which is git-ignored) to use PostgreSQL instead, for example
`postgresql+psycopg://<user>:<password>@<host>/<database>`. Never commit a real URL; the app never prints it. Tables
are created on first use. See [docs/database.md](docs/database.md).

## How the scoring works

- [Scoring function](docs/scoring_function.md): statement to probability of default, score, risk tier, reasons and
  the estimated limit; the score formula and tier bands are defined there.
- [Scorecard mapping](docs/scorecard_mapping.md) and [scorecard report](docs/scorecard_report.md): the cash-flow
  scorecard that the simulated outcomes are drawn from, and how predictable those outcomes are.
- [Model report](docs/model_report.md): logistic regression, random forest and XGBoost against the baselines.
- [Calibration report](docs/calibration_report.md): calibration, bootstrap intervals and the tier check for the
  deployed model.
- [Sensitivity report](docs/sensitivity_report.md): the same comparison under other scorecard weights.

## The app

Vendors check scores, apply and follow their applications; lenders review a queue, decide and record repayment
outcomes; admins see platform counts, manage accounts, read the audit log and export recorded outcomes. Overview of
the roles, pages and privacy rules: [docs/app_overview.md](docs/app_overview.md). Repayment tracking and the export:
[docs/repayment_outcomes.md](docs/repayment_outcomes.md).

## Limitations and next steps

- **Simulated data.** Nothing is validated on real repayment
  ([calibration report: Limits](docs/calibration_report.md#limits), [assumptions](docs/assumptions.md#3-known-limitations)).
- **Small test set, wide intervals.** The models cannot be ranked against each other on this data
  ([calibration report](docs/calibration_report.md#how-much-a-small-test-set-moves)).
- **Placeholder loan-limit policy.** The tier factors behind the estimated limit are not from any lender
  ([scoring function](docs/scoring_function.md#estimated-eligibility-prototype-policy)).
- **No statement-ownership check.** The app does not verify that a statement belongs to the vendor who uploads it
  ([app overview](docs/app_overview.md#limitations)).
- **No database migrations.** New tables are created automatically; new columns need a manual step
  ([database](docs/database.md#schema-changes-no-migration-tool)).
- **Three-class outcome planned.** On time, late and default are modelled only as a secondary experiment so far
  ([three-class report](docs/model_report_3class.md), [outcome mapping](docs/repayment_outcomes.md#mapping-to-the-three-outcome-classes)).

## Testing

```
pytest -q
```

The tests marked `postgres` run the database tests against PostgreSQL. They are skipped locally unless
`DATABASE_URL` points at a PostgreSQL test database, and they run in GitHub Actions on every push
(`.github/workflows/tests.yml`). See [docs/database.md](docs/database.md#tests).
